What every LLM request can see—and what it cannot

This code-derived inventory now includes the smallest standardization proposal: one context builder, five optional allowlist flags chosen locally by each pipeline, and the existing task-specific prompts left where they are.

Recommendation

The builder owns mechanics; each pipeline owns policy

Standardize only the reusable base context. The builder returns context messages; each existing pipeline names only the sources it wants and still appends its own prompt, target content, guidance, schema, and transport settings. Every omitted source defaults to false; there is no central object naming or grouping the pipelines.

The design rule The shared service knows “history” and “Memories.” It never knows “Chat response,” “Plan work,” “Book summary,” or any other caller identity.

Smallest useful boundary

Build base context, then append the task

The shared code does not know about prompts, models, schemas, discussions, or output parsing. It only answers: “Which reusable Story Vault context should precede this task?”

1 Name only wanted sources

An omitted flag is false. A present flag can only be true.

2 Build context once

One service fetches only selected sources. For history it uses configured retention, optionally includes Plans or the recent scene, then inserts selected durable context.

3 Append existing task messages

The feature service adds its current prompt, target entity, summaries, feedback, discussion transcript, or character metadata exactly as it does today.

4 Call the existing API

Text, stream, structured output, model selection, request settings, and labels remain unchanged and outside this refactor.

The whole shared API

An additive allowlist with safe defaults

The interface names available sources, not request types. The ?: true form prevents noisy false declarations and makes every call read as “include these.”

Proposed context builder No shared presets, request registry, transport abstraction, or contributor pipeline. 
interface LLMContextSelection {
  history?: true;
  memories?: true;
  characterSheets?: true;
  plans?: true;
  recentHistoryOnly?: true; // fixed last 12 projected messages
}

interface LLMContextInput {
  beforeMessageId?: string;  // regeneration only
  historyOverride?: readonly LLMMessage[]; // frozen Chapter snapshot only
}

async function buildLLMContext(
  chatId: string,
  selection: LLMContextSelection = {},
  input: LLMContextInput = {},
): Promise<LLMMessage[]>;

const messages = [
  ...await buildLLMContext(chatId, {
    history: true,
    memories: true,
    characterSheets: true,
    plans: true,
  }),
  system(chatSettings.prompt),
  ...optionalGuidance(guidance),
];

return openRouter.postChatStream(
  messages,
  model,
  "chat",
  "Chat",
  requestSettings,
);
history

Include projected Story, Books, Chapters, chat messages, Notes, reasoning, and clarifications. Always use current system/chat settings.

memories

Insert the chat’s nonblank Memories using the existing durable-context placement rule.

characterSheets

Insert sheet items for tracked, active characters. Appearance remains task-specific.

plans

Include all visible Plans. If omitted, Plans are excluded from projected history.

recentHistoryOnly

Keep the latest 12 persisted projected messages. Ignored when history is omitted.

Could this be four flags?

Yes: combine memories and characterSheets into durableContext. The cost is a real behavior change for Book summary/title: those requests must either gain Memories or lose Character Sheets. Five is the minimum for near-parity; four is the absolute minimum if that change is acceptable.

Pipeline-owned policy

Each caller declares exactly what it wants

Similar pipelines may repeat the same few inclusions. That small duplication is preferable to coupling unrelated callers through a central preset name.

Dependencies point inward

A feature depends on the generic builder. The builder never imports or names a feature pipeline.

Policy is visible at the call site

A reviewer sees named inclusions beside the prompt; every unmentioned source is excluded.

Changes stay local

Changing Book context does not require editing a shared catalog used conceptually by other pipelines.

Explicit tradeoffs

Functionality that would change

The simplification comes from deleting special policies. These are the behavior changes required to get from today’s inventory to five optional, false-by-default flags.

One projection policy everywhere

Every history-enabled request respects the system chapter buffer and the chat’s reasoning retention. Plans, images, character tools, and discussions stop using the hidden “6 messages + unlimited reasoning” defaults.

Plans become all-or-nothing

Omitting plans removes every Plan. Plan work therefore stops seeing other Plans even when today’s hideOtherPlans setting would allow them. The current Plan is still appended separately.

Recent means one fixed window

recentHistoryOnly: true always means the latest 12 persisted projected messages. Active-character selection keeps its approximate current scope without a general selection language.

Chapter snapshot uses configured policy

The click-time snapshot remains, but it should be captured with the configured builder. A non-default chapter buffer can therefore change which trailing messages reach the Chapter title/summary request.

Existing duplication is not solved here

Story/Chapter/Book discussions can still repeat current entity content, and Character Sheet Sync can still repeat sheet items as task input. Deduplication is deliberately outside this minimum refactor.

Prompts and transports do not change

Response prompts, reasoning prompts, schemas, labels, model selection, discussion transcripts, summaries, appearances, feedback, streaming, and parsing remain owned by their current feature services.

Minimal implementation

Three moves, then stop

This is a context cleanup, not a new request architecture. Resist adding a catalog, executor, contributor interface, or generalized selector until a real second use appears.

Add the generic builder

Reuse configured projection and durable-context insertion behind the five-flag allowlist. Add no shared caller presets.

Replace context assembly only

Each LLM workflow names its wanted sources locally, appends its existing task messages, and keeps its existing OpenRouter call.

Lock the five inclusions

Test the selection at each call site, plus builder ordering, regeneration/snapshot behavior, and an architecture check preventing direct projection reads.

The current problem this replaces

Today there are two meanings of “projected history”

The allowlist builder would eliminate the default path: every history: true request would use configured projection.

Configured projection

Built through LLMMessageContextService.

  • Uses the system’s trailing-chapter message count.
  • Uses the chat’s reasoning enabled/expiration settings.
  • Can then insert Memories and tracked, active Character Sheets.

Default projection

Direct calls to LLMChatProjection.GetMessages().

  • Always uses a trailing chapter buffer of 6.
  • Uses reasoning retention null: uncompressed reasoning never expires.
  • Does not add Memories or Character Sheets.

Questions surfaced · documentation only

The most consequential inconsistencies

These are review questions, not proposed code changes. Some may be deliberate product choices.

Direct callers keep reasoning indefinitely

Plans, discussions, character description/selection, and image prompts use default retention null, regardless of chat reasoning settings.

Durable facts stop at family boundaries

Memories and Character Sheets reach core chat, Agent Intent, and Sheet Sync—but not Plans, most discussions, or image/character prompts.

Active-character selection drops fetched context

It builds configured durable context, then keeps only ID-bearing messages, removing the Memory and Character Sheet messages it just loaded.

Entity discussions are not deduplicated consistently

Plan discussion excludes its own Plan before adding current content. Story, Chapter, and Book discussions generally include and repeat their targets.

Narrow book requests are coherent

Book summary/title intentionally use selected chapter summaries and Character Sheets rather than the entire chat. New Book discussion is narrower still.

Response prompts are correctly specialized

The chat response prompt appears only in continuation responses. Reasoning, regeneration, analysis, and maintenance requests use their own workflow prompts.
