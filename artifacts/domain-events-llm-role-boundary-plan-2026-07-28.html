Architecture decision · Story Vault · 28 July 2026

Persist meaning. Compile protocol roles later.

Removing raw LLM roles from new events is the right boundary. It does not fix Sonnet by itself. The controlled Sonnet 4.5/5 comparison confirmed one failing shape: a reasoning-as-assistant turn followed by a trailing system prompt. Keep the user-configured response prompt at the end, but compile it as a user task instead.

✓

Confirmed by the four-case model probe

Do not persist role. Do persist who authored the text, encoded as domain events such as UserMessageCreated and AssistantResponseCreated. The LLM adapter alone should decide whether those facts become user, assistant, system, or consolidated prompt content.

The boundary

Authorship is domain data; role is wire data

Eliminating both would make the UI and future projections unable to distinguish a human turn from generated prose.

Keep as durable facts

  • A user added text.
  • Story Vault generated a response.
  • A reasoning artifact was generated.
  • A story, plan, note, chapter, or book changed.
  • Stable IDs used by editing, deletion, compression, and summaries.

Remove from persisted models

  • role: "user" | "assistant" | "system".
  • The generic MessageCreated(role, content) writer.
  • AddSystemMessage, which has no production caller today.
  • LLM terminology in domain projections and event utilities.
  • Assumptions that one stored item always equals one wire message.

Latest finding

The failure is the transition, not system messages generally

Sonnet 4.5 returned content for all four requests. Sonnet 5 returned content for three; only case 3 failed. That isolates the incompatible tail to assistant → system after reasoning.

1 · Passed

system → user → system

2 · Passed

system → user → user

3 · Sonnet 5 failed

system → user → assistant → system

4 · Passed

system → user → assistant → user

Conclusion: do not broadly ban terminal system messages based on this test. Repair the response path by compiling its trailing task as user, which changes only the failing transition and preserves prompt recency.

Why cleanup alone is insufficient

The compiler must change the final sequence

Moving the same mapping out of the event model would reproduce the same failure. The actual fix is the target request shape.

Current response request

user The user’s story turn.
assistant Persisted ReasoningCreated projection.
system The chat response prompt appended at the end.
The probe reproduced this exact assistant → system tail: Sonnet 4.5 succeeded, while Sonnet 5 returned no content.

Target response request

system Optional, minimal app-owned rules that are truly stable.
user Story content, selected durable context, and conversation turns remain near their chronological positions.
assistant Reasoning artifact, if retained as an assistant turn.
user The full user-configured chatSettings.prompt, framed as the immediate response task.
The response prompt stays maximally recent and Sonnet receives the required terminal user turn.

No duplication is required for the first fix. chatSettings.prompt is already user-configurable and response-specific, so keep its full content at the end as user. Reserve a leading system message for minimal application-owned rules, if Story Vault actually needs any.

Recommended sequence

Fix compatibility first, then clean the model

The request change is small and validates the diagnosis. The event migration is broader, but the controlled probe now gives both changes a concrete regression contract.

Compatibility patch

Change the final chatSettings.prompt from toSystemMessage(...) to toUserMessage(...). It stays recent and gives Sonnet a valid conversational ending.

→

Architectural cleanup

Replace new generic role-bearing events with semantic event types. Keep legacy reads working at the event-store boundary.

Migration plan

Five safe, separable changes

Each phase has an observable outcome and can be reviewed without rewriting persisted chat history.

Repair request order

Compile the response prompt as the final user task. Add a Sonnet regression test around reasoning → response.

Add semantic events

Introduce UserMessageCreated and AssistantResponseCreated with IDs and content only.

Normalize legacy data

Convert old MessageCreated roles at the existing normalization boundary. Do not rewrite stored event blobs.

Update projections

UI, compression, history maintenance, and editing consume event semantics—not LLM roles. Preserve existing visible behavior.

Delete old writers

Remove MessageCreatedEventUtil, AddSystemMessage, role-based projection mapping, and obsolete tests after replay coverage passes.

Completion criteria

The boundary is real only if tests enforce it

These checks distinguish a structural improvement from a type rename.

New persisted chat events contain no LLM role field.

Old role-bearing chats replay to the same UI timeline and stable IDs.

Only the LLM request layer imports or constructs LLMMessage.

Reasoning followed by response generation ends with a user message.

The full configured response prompt remains last and is compiled as user.

No system-role message is inserted after conversational turns begin.

Sonnet 5 and existing configured models return non-empty streamed content.

Editing, deletion, chapter coverage, compression, and continuity boundaries retain their behavior.

No new generic “system message” domain operation remains.
