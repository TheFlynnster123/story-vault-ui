Story Vault request anatomy · source review · 28 July 2026

Eleven message types become three roles.

The UI type is not what OpenRouter sees. Before a request leaves Story Vault, timeline events are projected into user, assistant, or system messages—and the type metadata is stripped.

!

Your theory is plausible, and the sharpest suspect is terminal system.

Core chat, reasoning, plans, image-prompt generation, and several “generate from discussion” actions deliberately end their outbound arrays with a system message. A model/provider that expects the final turn to be user could therefore fail consistently by workflow, even when the selected model otherwise works.

What the app shows vs. what the model receives

The request cleaner sends only { role, content }. Timeline labels such as plan and chapter never reach OpenRouter as a message “type.”

Exact mapping

Every timeline type, decoded

“Wire role” means the role after LLM projection. The content wrappers are significant prompt text, but they do not create new protocol roles.

Timeline type Wire role What it represents Wire content
story system The current story/world context, inserted at the start. # Story followed by story text.
user-message user A human chat turn. Raw text, unless an older eligible message is compressed.
system-message system An ordinary persisted message explicitly created with system role. Raw text, unless compressed.
assistant assistant A generated chat response. Raw text, unless compressed.
reasoning assistant A separately generated and persisted reasoning step. [Reasoning] … [End of Reasoning].
civit-workflow not sent Image-job state, cost, model, and workflow metadata. No LLM projection handler or LLM context item type.
chapter system A summary replacing covered messages in durable context. [Previous Chapter Summary: …] wrapper.
book system A summary replacing covered chapters. [Book Summary: …] wrapper.
plan system The latest visible instance of a named generated plan. [Plan: …] … [End of Plan].
note system Persistent user feedback, optionally expiring after N messages. [Note] … [End of Note].
agent-clarification system A saved question/answer pair from an agent workflow. [User Clarification] with question and answer.

Terminal role by request path

The last item is often added after chat history

The latest timeline event does not necessarily determine the final wire role. Request builders append task instructions after projected history.

Normal chat response

Appends the chat’s response prompt after all durable context. With no one-off guidance, that prompt is last.

ends system

Reasoning generation

Usually sends one consolidated system message containing context plus reasoning instructions.

ends system

Plans & plan suggestions

Both consolidated and unconsolidated builders place the plan instruction in the final system message.

ends system

Image-prompt generation

The image instruction—and regeneration feedback—are appended as system messages.

ends system

Generate from discussion

Story, chapter, and book finalization paths often use a trailing system instruction; some send only that one system message.

ends system

Helper & maintenance jobs

Character selection, sheets, agent intent, compression, continuity refresh, chapter drafts, and book summaries append a concrete user task.

ends user

Chat with guidance

Guidance is appended after the response or reasoning prompt, so it converts those requests to a terminal user turn.

ends user

Regenerate response

Feedback makes the last role user. Without feedback, the request simply ends wherever truncated history ends.

variable

New story & discussion turns

The basic story generator, discussion replies, and discussion openers finish with an explicit user instruction.

ends user

Interpretation

What the code proves—and what it does not

Strong repository evidence

  • Failures can cluster by feature because terminal roles cluster by feature.
  • The dominant unusual pattern is a trailing system message.
  • The request boundary strips IDs and types, so models cannot reject plan or note as protocol types.
  • Adding guidance is already a clean A/B switch from terminal system to terminal user.

Not yet proven

  • No per-model terminal-role capability matrix exists in this repository.
  • OpenRouter’s public chat schema accepts system, user, and assistant messages generally; it does not promise every upstream model treats every ordering identically.
  • A 400 can support a formatting mismatch; 402, 429, 502, or 503 usually point elsewhere.
  • The error body and exact upstream transformation are needed to attribute a failure confidently.

Working conclusion: model compatibility should be analyzed against terminal wire role, not the visible Story Vault message type.

Fast validation

A four-part experiment isolates the variable

Keep model, provider settings, prompt text, and history constant. Change only the role of the final instruction.

Record

For every tracked request, capture model, feature label, final role, status, HTTP status, and raw provider error.

Pair

Run the same minimal instruction once as trailing system and once as trailing user.

Cross

Repeat for the suspect models and at least one known-good model through the same Story Vault backend.

Decide

If only terminal system fails with 400-class provider errors, normalize task prompts to user role or add a compatibility rule.
