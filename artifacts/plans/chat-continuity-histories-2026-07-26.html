Story Vault · General continuity architecture

Give the whole story a set of living histories.

Histories are LLM-maintained, topical views of what has changed across a chat. Each one follows a subject over time and is recalled only when the current request needs it.

✓

Character Sheets remain as they are. They are one specialized source of character context. Histories fill the broader continuity gap around plot threads, places, objects, factions, relationships, mysteries, promises, and world state.

The lifecycle: notice, update, select, recall

Generation happens when the story changes. Inclusion happens when a request is assembled. Those are related decisions, but they should not be the same operation.

1

Observe the delta

Use only the turns since the last continuity pass.

2

Route changes

Identify affected histories and propose new ones when warranted.

3

Write revisions

Update only affected documents and retain their prior versions.

4

Select for a request

Choose histories from recent subjects, intent, metadata, and pins.

5

Render and trace

Insert chosen revisions before the recent tail and record why.

Two loops, with different jobs

The write loop can resemble the current periodic Plan refresh. The read loop belongs in request context assembly and runs against each request’s temporal boundary.

Background or periodic · write loop

Maintain histories with an LLM

The model receives the old revision, new messages, and the History’s tracking instructions—not the entire chat by default.

1 Detect material changes and affected subjects.
2 Return structured update proposals with source message IDs.
3 Accept automatically, review, or edit by History preference.
4 Save a new revision with an “updated through” boundary.

“Only when necessary” needs explicit rules

Relevance should be observable. A selector may use an LLM, but it should return History IDs and reasons—not rewrite the histories while choosing them.

Manual inclusion wins

Always-included or explicitly requested Histories bypass ranking.

Metadata first

Select from title, scope, aliases, subjects, and routing hints before loading bodies.

Request-aware recall

A story reply, chapter summary, image prompt, and regeneration can select differently.

Time cutoff is absolute

A request at message N can only use a revision whose coverage ends at or before N.

A focused first implementation

Start with user-created Histories and transparent selection. Let automatic discovery follow once the document lifecycle is reliable.

1

Definitions + revisions

Add managed storage, manual CRUD, a prompt, refresh interval, revision history, and source-message boundaries.

2

LLM maintenance

Generate or update one History from its prior revision and the messages since it was last updated.

3

Selective context

Add manual/automatic inclusion and a structured selector that returns IDs, reasons, and temporal-safe revisions.

4

Discovery + compaction

Suggest new Histories from recurring subjects; merge or archive stale ones only after real usage reveals the need.

The important failure modes

A History system is useful only if it recalls less context without making continuity less trustworthy.

Watch for

  • Too many overlapping Histories restating the same events.
  • Updates drifting from source material over repeated revisions.
  • Plans or speculation being recorded as things that happened.
  • Later knowledge leaking into regeneration of an earlier scene.
  • Selection latency becoming larger than its token savings.

Prove it with

  • Source IDs and “updated through” shown on every revision.
  • A context inspector listing selected Histories and reasons.
  • Golden scenarios for relevant inclusion and irrelevant exclusion.
  • Temporal tests for regeneration before and after each revision.
  • Token and latency comparisons against the current context bundle.
→

The useful abstraction is a “living context lens.”

Each History answers one durable question about the story across time. The LLM maintains it; metadata routes it; the context assembler recalls it. Existing features keep their current responsibilities.
