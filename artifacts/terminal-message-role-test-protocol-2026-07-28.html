Controlled experiment · Story Vault · 28 July 2026

Change the final role. Nothing else.

First use the current UI for a quick signal. Then use a paired probe with identical payloads for proof. Judge transport errors, not whether the prose is “good.”

Independent variable Final message role: system vs user.
Held constant Model, settings, content, history, and request order.
Measured outcome Accepted/error, HTTP status, raw body, and non-empty response.

Phase 1 · Prepare

Remove the obvious confounders

This makes the request list readable and prevents a reasoning failure from being mistaken for a chat failure.

Pick one model

Start with a model that has failed consistently. Keep the exact model slug and advanced settings unchanged.

Disable reasoning

Reasoning creates its own request before chat. Turn it off so one send produces one relevant Chat request.

Disable retries

Set retries to zero if the model settings expose it. Otherwise, treat multiple rows from one action as attempts of one case.

Keep the session

Set monitoring to retain enough requests, then do not reload. Request history exists only in this running app session.

Use the same tab. After each run, navigate to /chat/<chatId>/credits via “Credits / Recent Requests.” A reload or separate tab starts a different in-memory tracker.

Phase 2 · Quick UI smoke test

Use normal Send versus Send with Guidance

This is available today and can reveal a strong correlation. It is not fully controlled because adding guidance also adds content.

Case A · Normal Send

last role: system

  1. Use a fresh minimal chat with the suspect model.
  2. Send Reply exactly ROLE_PROBE_OK.
  3. Open the resulting request in Recent Requests.
  4. Confirm the last context card is system.
  5. Click Copy debug and save the JSON.
VERSUS

Case B · Send with Guidance

last role: user

  1. Use a second fresh chat with identical configuration.
  2. Long-press Send to open “Send with Guidance.”
  3. Use Reply exactly ROLE_PROBE_OK as guidance.
  4. Confirm the final context card is user.
  5. Copy the debug JSON and compare status and error body.

If A fails repeatedly while B succeeds, the hypothesis becomes credible—but still not proven, because the two requests are not byte-for-byte identical apart from role.

Phase 3 · Definitive paired probe

Send two payloads that differ in one field

The clean implementation is a small developer-only probe inside Story Vault that calls the existing OpenRouter service twice and records both requests normally.

Payload S

terminal system

[ { "role": "system", "content": "You are a protocol test." }, { "role": "system", "content": "Reply exactly ROLE_PROBE_OK" } ]
ONLY ROLE CHANGES

Payload U

terminal user

[ { "role": "system", "content": "You are a protocol test." }, { "role": "user", "content": "Reply exactly ROLE_PROBE_OK" } ]

Alternate execution order (S→U, then U→S) and repeat the pair. This reduces the chance that a temporary provider outage, rate limit, or routing change happens to align with one role.

Capture from Request Inspector

  • Resolved model string
  • Model/request parameters
  • Every input role and content
  • HTTP status and displayed error
  • Response body, including an empty body

Verify before counting a run

  • The final role is the intended role.
  • The model and parameters match its pair.
  • No unexpected guidance or history was appended.
  • The attempt was not merely an automatic retry.
  • The response was non-empty if marked successful.

Phase 5 · Decide

Interpret transport evidence conservatively

A role-compatibility claim needs a stable split by final role, not merely different writing quality.

Supports the theory

System-terminal requests repeatedly receive 400-class schema/order errors while paired user-terminal requests succeed through the same model and settings.

Weakens the theory

Both roles succeed, both fail with the same error, or failures do not track the final role when the execution order is reversed.

Inconclusive

401/402 authentication or credit errors, 429 rate limits, 503 availability failures, or inconsistent 502 provider failures.

Why a small in-app probe is the cleanest next step

It reuses the existing authentication, encryption key, backend, model settings, retry behavior, and Request Tracker. A standalone curl script would need to reproduce those layers and could accidentally test a different route than the application.

Completion criterion: for each suspect model, paired debug bundles show matching payloads and settings with only the terminal role changed.
